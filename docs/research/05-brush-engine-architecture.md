## 1. MyPaint / libmypaint — the brush model to adopt

libmypaint is the best-documented open engine: a pure C state machine (`mypaint-brush.c`) that consumes timestamped pointer events and emits abstract `draw_dab()` calls; the surface backend is pluggable ([mypaint-brush.c](https://github.com/mypaint/libmypaint/blob/master/mypaint-brush.c), [mypaint-surface.h](https://github.com/mypaint/libmypaint/blob/master/mypaint-surface.h)). The entire parameter set — inputs, settings, states — is one JSON file ([brushsettings.json](https://github.com/mypaint/libmypaint/blob/master/brushsettings.json)).

**Core model (adopt wholesale):**
- **Settings vs. states split.** Settings are constant during a stroke (size, spacing, curves); states mutate during the stroke (position, filtered speed, smudge color, "time/distance to next dab"). This is stated verbatim in the `mypaint-brush.c` header ([source](https://github.com/mypaint/libmypaint/blob/master/mypaint-brush.c)). This split is what makes a brush preset serializable and a stroke replayable.
- **Inputs → curves → settings composition.** Inputs: `pressure`, `random`, `stroke`, `direction`, `tilt_declination/ascension`, `speed1` (fine), `speed2` (gross), `custom`, `viewzoom`, `brush_radius`, `barrel_rotation`, `gridmap_x/y` ([brushsettings.json](https://github.com/mypaint/libmypaint/blob/master/brushsettings.json)). Each setting = **base value + Σ per-input user-drawn curve Y(x)**; every input drives every setting through an editable curve. This "curve widget parameter model" is the single most copyable UI/design idea in open brush engines.
- **Spacing algorithm.** Not a fixed "spacing %" but *dab density*: `dabs_per_basic_radius` (dabs per one base-radius of travel), `dabs_per_actual_radius` (per current dynamic radius — this is adaptive spacing by pressure/size for free), and `dabs_per_second` (airbrush; independent of movement). The simulation carries **residual fractional dabs** between events (`partial_dabs` state, `dabs_todo = count_dabs_to(x, y, dtime_left)` called once per event even if zero dabs fire, because radius can change faster than dab rate) ([mypaint-brush.c](https://github.com/mypaint/libmypaint/blob/master/mypaint-brush.c), [brushsettings.json](https://github.com/mypaint/libmypaint/blob/master/brushsettings.json)).
- **Velocity via first-order low-pass.** `fac = exp(-dt/T1); output = fac*output + (1-fac)*input` — MyPaint's documented filter used for speed and tracking; filtered velocity = `input - output` when input is position ([MyPaint backend docs](https://www.mypaint.app/en/docs/backend/brush-engine)). Physical speed is mapped through `y = log(gamma+x)*m + q` (slowness = T1, gamma controls log-vs-linear response) ([mypaint-brush.c](https://github.com/mypaint/libmypaint/blob/master/mypaint-brush.c)). Two speeds: fine (`speed1_slowness` 0.04 default) and gross (`speed2_slowness` 0.8).
- **Logarithmic radius.** `radius_logarithmic`: 0.7 ≈ 2 px, 3.0 ≈ 20 px; actual radius = e^value. Krita's docs explain the consequence: preset radius 2.0 → e^2.0 = 7.389 px radius ([Krita MyPaint engine docs](https://docs.krita.org/en/reference_manual/brushes/brush_engines/mypaint_engine.html)). Clamped `ACTUAL_RADIUS_MIN 0.2` / `ACTUAL_RADIUS_MAX 1000` as a safety guard against dynamics explosion ([mypaint-brush.c](https://github.com/mypaint/libmypaint/blob/master/mypaint-brush.c)).
- **Opacity linearization.** Overlapping dabs compound: N dabs at per-dab alpha a reach 1−(1−a)^N. `opaque_linearize` (default 0.9) estimates dabs-per-pixel from spacing and solves for per-dab alpha so the *stroke* reaches the requested opacity — "0.0 the opaque value is for the individual dabs; 1.0 it is for the final brush stroke, assuming each pixel gets dabs_per_radius*2 dabs on average" ([brushsettings.json](https://github.com/mypaint/libmypaint/blob/master/brushsettings.json); the estimator lives in `mypaint-brush.c`).
- **Hardness / feather.** `hardness` (falloff center→edge) + `anti_aliasing` "pixel feather" (0=off, 1=blur 1px, kills staircase on small brushes) are *separate* — a good distinction to keep ([brushsettings.json](https://github.com/mypaint/libmypaint/blob/master/brushsettings.json)).
- **Per-dab surface contract.** `draw_dab(x, y, radius, rgb, opaque, hardness, softness, alpha_eraser, aspect_ratio, angle, lock_alpha, colorize, posterize, posterize_num, paint_mode)` — a clean dab ABI to mirror as a Rust trait / WGSL struct ([mypaint-surface.h](https://github.com/mypaint/libmypaint/blob/master/mypaint-surface.h)). Note the **smudge bucket** system (MyPaint 2.0: up to 255 stored sampled colors per brush) and `smudge_length` semantics: 1.0 = never resample (fast), 0.0 = resample every dab ([brushsettings.json](https://github.com/mypaint/libmypaint/blob/master/brushsettings.json)).
- **Slow position tracking** (`slow_tracking`): lowpass on position itself = MyPaint's built-in stabilizer, distinct from speed filtering; plus `slow_tracking_per_dab` for dab-domain smoothing ([brushsettings.json](https://github.com/mypaint/libmypaint/blob/master/brushsettings.json)).

**Skip / defer:** spectral pigment mixing (`paint_mode`), posterize, gridmap inputs, 255 smudge buckets — all post-MVP. Keep the *state list* append-only like upstream does (replay-file compatibility note in brushsettings.json).

## 2. Krita — stroke scheduling, tiles, undo, smudge

**Strokes framework (the reason Krita's UI never blocks):** Every user line = a `KisStroke` composed of **stroke jobs** (init → dabs → merge/commit); jobs are added **incrementally while the user paints**. Jobs are typed `CONCURRENT` (parallel with other concurrent jobs), `BARRIER`/sequential (FIFO order guaranteed), or `EXCLUSIVE` (scheduler halts everything). `KisStrokesQueue::processOneJob` runs whenever a worker thread frees; strokes never run interleaved with each other; a two-queue scheduler (strokes + viewport updates) balances threads by image area ([Strokes queue — Krita technical docs](https://docs.krita.org/en/untranslatable_pages/strokes_documentation.html), [Krita/Strokes Framework wiki](https://community.kde.org/Krita/Strokes_Framework)). A 2022 commit fixed QThreadPool discarding threads — i.e., Krita keeps a persistent worker pool for the scheduler ([invent.kde.org commit](https://invent.kde.org/graphics/krita/-/commit/39fcfac8281d4d0bf100d4c15460fa2a2bc998ab)).

**Undo via post-execution:** strokes use `KisPostExecutionUndoAdapter` — painting happens immediately on worker threads; the undo command is registered *after the fact*, and its first `redo()` is a no-op because the pixels are already painted ([strokes doc](https://docs.krita.org/en/untranslatable_pages/strokes_documentation.html)). This decouples "make pixels now" from "record history".

**Tile store:** paint devices are auto-extending grids of **64×64 tiles**, compressed/swapped under memory pressure; "the undo system stores copies of entire tiles" ([Krita technical overview](https://github.com/KDE/calligra-history/blob/master/krita/doc/krita_technical_overview.html)). The tiles3 engine replaced per-transaction memento hashtables with a **centralized history store** keyed by `KisTransactionData` lifetime — deleting an undo command frees the history it points at; "historical" tiles (referenced only by history, `mementoed() && numUsers() <= 1`) are swapped out first ([Transactions Design](https://community.kde.org/Krita/Transactions_Design), [KisTileData docs](https://srcdoc.krita.maou-maou.fr/classKisTileData.html), [developer walkthrough](https://krita-artists.org/t/how-does-undo-and-redo-code-work/66511/4)). **Cumulative Undo** merges similar old strokes by time-gap rules to keep history cheap ([Undo History docker](https://docs.krita.org/en/reference_manual/dockers/undo_history.html)).

**Opacity vs. flow (adopt this exact semantics):** Opacity = stroke transparency; Flow = per-dab transparency; since 4.2 they **multiply** (previously they added, which was wrong vs. every other app) ([Opacity and Flow](https://docs.krita.org/en/reference_manual/brushes/brush_settings/opacity_and_flow.html)). **Painting mode:** *Build-up* treats opacity like flow (dabs accumulate to full); *Wash* treats opacity as stroke-level cap — implemented as **indirect painting**: the stroke paints into a temporary layer, which is merged at stroke end ([Opacity and Flow](https://docs.krita.org/en/reference_manual/brushes/brush_settings/opacity_and_flow.html), confirmed by a dev: "Wash is an indirect painting mode, creates a temporary layer at the start of the stroke... then merges it at the end" ([krita-artists](https://krita-artists.org/t/how-to-programmatically-draw-by-pixel-engine/182564/2))). Pixel brush tips are multithreaded since 4.0 ([Pixel Brush Engine](https://docs.krita.org/en/reference_manual/brushes/brush_engines/pixel_brush_engine.html)).

**Smudge engine:** Color Smudge = sample canvas under dab, blend sample with brush color ("Color Rate"), paint back. `Smudge Length` = how much of the previous dab's sampling is retained (100% never decays ⇒ spreads forever; decay depends on spacing & opacity — more dabs = more samples = smoother smear). Two modes: **Smear** (transports sampled color, fades in size) vs **Dulling** (re-fills dab from a fresh, possibly larger `Smudge Radius` sample each dab — keeps brush shape). Overlay toggle samples the full layer composite instead of just the current layer ([Color Smudge Brush Engine](https://docs.krita.org/en/reference_manual/brushes/brush_engines/color_smudge_engine.html)). Airbrush option: keeps adding color while stationary at a rate ([Options](https://docs.krita.org/en/reference_manual/brushes/brush_settings/options.html#airbrush)) — pair with MyPaint's `dabs_per_second` for the same effect.

**Why Krita strokes feel good (checklist):** input never paints on the UI thread; dab jobs stream incrementally into an executing stroke; wash temp layer gives clean flow semantics without per-pixel locks; persistent worker pool; spacing/sensors identical to the preset preview.

## 3. Substance Painter — implementation semantics

- **Flow vs. Stroke Opacity:** Flow = "intensity or opacity of the individual stamps inside the brush stroke" (pressure-mappable). Stroke Opacity = "maximum global opacity of a brush stroke... applied at the end of the stroke drawing process" — hence **cannot** be pressure-driven and never self-overlaps within one stroke ([Paint brush — Adobe docs](https://experienceleague.adobe.com/en/docs/substance-3d-painter/using/painting/paint-tools/paint-brush)). Introduced in SP 2.5 (2017): "opacity controls the overall intensity of a brush stroke, contrary to the flow setting which controls the intensity of each individual stamp... possible to paint and repaint a same area without creating overlapping values" — plus the **"A" modifier to continue the previous stroke** instead of starting a new accumulation ([SP 2.5 release notes](https://experienceleague.adobe.com/en/docs/substance-3d-painter/using/release-notes/old-versions/version-2-5)). Implementation: flow multiplies per-dab alpha; stroke opacity is a per-stroke accumulation buffer max/ALPHA_DARKEN pass — i.e., Krita Wash + a cap, minus pressure.
- **Spacing / Follow Path / jitter:** spacing = distance between stamps (Substance measures in % where 0 spacing still paints on click); Follow Path orients stamps along stroke direction computed from previous→current stamp (so a single click paints nothing with it enabled); size/flow/angle/position jitter per stamp ([Paint brush docs](https://experienceleague.adobe.com/en/docs/substance-3d-painter/using/painting/paint-tools/paint-brush)).
- **Hardness** = per-stamp radial falloff toward edge; when an alpha (grayscale mask) drives the stamp, hardness acts on the alpha's histogram (exposed Substance-graph `hardness` parameter can be remote-controlled by the toolbar shortcut) ([Paint brush docs](https://experienceleague.adobe.com/en/docs/substance-3d-painter/using/painting/paint-tools/paint-brush)). ArmorPaint confirms the same trio in open-source space: Radius / Opacity / Hardness ("fade opacity towards the brush stroke edge") ([ArmorPaint manual](https://github.com/armory3d/armorpaint_web/blob/main/manual.md)).
- **Lazy Mouse:** "a distance offset between the mouse cursor and the actual painting which allows to paint more precise or smooth strokes" — i.e., string/leash smoothing, shown as a gray circle ([Lazy mouse docs](https://experienceleague.adobe.com/en/docs/substance-3d-painter/using/painting/lazy-mouse)).
- **Seam handling:** padding modes **2D Space Neighbor** (copy island-edge pixels outward — for opposed islands) and **3D Space Neighbor** (default: "look at the other side of the UV seam to find the neighbor pixel color" — for continuous painting across seams; not usable on the normal channel) ([Texture Set settings](https://experienceleague.adobe.com/en/docs/substance-3d-painter/using/interface/texture-set/texture-set-settings)). Padding is regenerated "infinite" (stretch until another island/edge), critical for mipmaps ([Texture dilation or Padding](https://experienceleague.adobe.com/en/docs/substance-3d-painter/using/technical-support/workflow-issues/export-issues/texture-dilation-or-padding)).

## 4. Stroke smoothing — one-euro, pull-cursor, stabilizers

**One-euro filter (Casiez, Roussel & Vogel, CHI 2012):** first-order low-pass with **adaptive cutoff** `fc = fc_min + β·|d̂x|` — low cutoff at low speed (kills jitter, tolerance for lag), high cutoff at speed (kills lag, tolerance for jitter); two intuitive parameters (min_cutoff, beta) + derivative cutoff (dcutoff, default 1 Hz) ([paper PDF](https://gery.casiez.net/publications/CHI2012-casiez.pdf), [homepage + tuning procedure](https://gery.casiez.net/1euro/), [ACM DL](https://dl.acm.org/doi/10.1145/2207676.2208639), reference implementations incl. timestamps-vs-freq handling: [casiez/OneEuroFilter](https://github.com/casiez/OneEuroFilter)). Tuning recipe from the authors: β=0, min_cutoff=1 Hz, raise min_cutoff until jitter acceptable, then raise β until lag acceptable ([homepage](https://gery.casiez.net/1euro/)). Production adopter: **Meta/Meta Quest Interaction SDK** ships it as the canonical pose/pointer filter ([OneEuroFilter class ref](https://developers.meta.com/horizon/reference/interaction/v205/class_oculus_interaction_input_one_euro_filter/)). Its sibling insight: MyPaint's `exp(-dt/T1)` lowpass is exactly the non-adaptive member of this family ([MyPaint docs](https://www.mypaint.app/en/docs/backend/brush-engine)).

**Pulled-string / dead-zone smoothing (event-based, distance-anchored):** Photoshop's stroke smoothing (0–100) offers **Pulled String Mode** — "the stroke follows a trailing anchor": paint only when the string is taut; cursor movement inside the radius leaves no mark (explicit dead zone) — plus **Stroke Catch-up** (paint continues toward cursor during pause), **Catch-up on Stroke End** (complete the line to the release point), and **Adjust for Zoom** (smoothing scales with zoom); a "brush leash" line visualizes the lag ([Adobe docs](https://helpx.adobe.com/photoshop/desktop/repair-retouch/clean-restore-images/create-smoother-more-polished-brush-strokes-with-stroke-smoothing.html)). This is the same family as Substance's Lazy Mouse ([docs](https://experienceleague.adobe.com/en/docs/substance-3d-painter/using/painting/lazy-mouse)).

**Krita's stabilizer:** a sample-count moving average over tablet events with **separate strength at min speed vs. max speed** ("a fast stroke needs less smoothing than a slow stroke"), an optional **Delay dead zone** ("adds a halo around the cursor... no stroke is made while the cursor is inside it"), Finish Line, Stabilize Sensors (smooths pressure/tilt too), scalable distance ([Freehand Brush Tool docs](https://docs.krita.org/en/reference_manual/tools/freehand_brush.html?highlight=stabilizer), options struct: [kis_smoothing_options.h](https://github.com/KDE/krita/blob/master/libs/ui/tool/kis_smoothing_options.h), origin: "Delayed Stroke"/stabilizer by Juan Luis Boya García, 2014 ([krita.org](https://krita.org/en/posts/2014/last-week-in-krita-weeks-25-26))). Users confirm the stabilizer adds visible input lag by design ([krita-artists](https://krita-artists.org/t/input-delay-when-using-stablizier/36918)).

**Recommendation:** one-euro as the always-on default (adaptive ⇒ near-zero cost when pen still, near-zero lag when fast — better than fixed sample-count averaging), pulled-string as an opt-in "lazy" mode, pressure through a separate one-euro instance. Perceptual budget: end-to-end latency under ~20 ms is the professional stylus target; >40 ms is noticeable lag ([threshold summary](https://us.ktcplay.com/blogs/technology-hub/stylus-latency-threshold-precision-work), academic treatment of latency effects on path-steering: [ACM](https://dl.acm.org/doi/10.1145/3613904.3642316)).

## 5. GPU dab compositing into paint layers

**Proof it scales:** ArmorPaint is "designed from scratch to run completely on the GPU," 4K painting on Intel HD4000-class iGPUs, 16K with an RTX 2080/8GB; brush node graphs are "evaluated for each painted stroke" and painting runs on D3D12/Vulkan/Metal ([armorpaint.org](http://armorpaint.org/), [manual](https://github.com/armory3d/armorpaint_web/blob/main/manual.md)). Mari's paint buffer reaches 16384×16384 bounded by GPU max texture size ([Mari paint buffer config](https://learn.foundry.com/mari/Content/user_guide/controlling_paint/configure_paint_buffer.html)).

**Batching dabs:** two proven shapes — (1) **instanced draws**: one quad (or the brush alpha mesh) per dab, per-instance attributes = {uv-pos, radius, color, opacity, angle, aspect}; GPU terminals do exactly this for glyphs ([GPU terminal architecture](https://terminal.ximg.app/technology.html)); (2) **compute**: a per-texel or per-dab dispatch writing via `imageStore`, as in the Godot community painter that renders brush coverage into an offscreen RT then resolves texel-by-texel into the atlas ([gpu-texture-painter](https://github.com/maantho/gpu-texture-painter)). For a compute-first wgpu engine: encode dab batches into a storage buffer (Dab struct ≈ libmypaint's `draw_dab` ABI, [mypaint-surface.h](https://github.com/mypaint/libmypaint/blob/master/mypaint-surface.h)), one compute pass per affected tile region with scissor-equivalent bounds, per-dab falloff evaluated analytically in the shader (hardness = smoothstep(hardness, 1, dist/r)), alpha texture sampled when present. **Premultiplied alpha: keep all layer textures premultiplied; dab output premultiplied; SRC-over order within a tile is sequential by construction (dab k+1 reads dab k's writes) — either one dispatch per dab within the same tile or R32F accumulation trick (see §6 wash buffer).**

**Partial updates for 4K–8K:** tiles (Krita: 64×64; a 256² tile is a good GPU default, matching Mari's patch workflows, [Mari features](https://www.foundry.com/products/mari/features)). Only re-encode/render tiles touched by the current dab batch (dirty-tile set from stamp bounds in UV space). Upload/download only those tile rects: partial texture updates are the standard tool (`copyTextureToTexture`-style region copies; Unity's `copyTextureToTexture` + `addLayerUpdate` pattern documents the same practice for array textures, [TSL/WebGPU guide](https://github.com/Makio64/advanced-threejs-tsl-webgpu-rendering)). Viewport never re-renders the layer: it samples the layer texture; a light dirty-tile copy to the viewport atlas (or texture array binding per UDIM) is all a frame needs.

## 6. Painting ON a mesh — the core 3D problem

**CPU reference implementation (Blender projective paint):** at stroke start, compute screen-space positions of vertices; per paint step, find triangles inside the brush disc; per pixel compute **barycentric coordinates** → UV → write brush pixels into the texture tile, threaded; supported by `seam_bleed` (extend paint beyond UV island bounds, in px), `use_occlude` (only paint directly-visible faces), backface culling, and normal falloff ([Psy-Fi GPU design doc](https://archive.blender.org/wiki/2015/index.php/User:Psy-Fi/GPU_Texture_Painting_Design), [API: ImagePaint.seam_bleed](http://archive.blender.org/documentation/blender_python_api_2_69_0/bpy.types.ImagePaint.html), [manual](https://docs.blender.org/manual/en/2.82/sculpt_paint/texture_paint/tool_settings/options.html)). The 2.4-era projection paint doc lists the artist-level mitigations still relevant: clone-with-offset **across** UV seams, geometry occlusion, 8 px bleed, screen→UV cache kept between strokes and regenerated while idle ([archived manual](https://archive.blender.org/wiki/2015/index.php/Doc:2.4/Manual/Textures/UV/Painting_the_Texture/Projection_Paint)).

**GPU projection (the design to port to wgpu/WGSL):** render the mesh into the layer texture *in UV space*: vertex shader tests each vertex against the brush disc in **screen space** (brush center/radius as uniforms); triangles fully outside the disc are collapsed/clipped; surviving triangles are emitted with `xy = uv`, `w = 1` (critical — avoids perspective distortion), keeping screen-space position as an attribute so the fragment shader evaluates the brush falloff in *screen* space and writes through a sampler for alpha-textured tips. Multiple render targets select the image/UDIM tile via a per-face flat attribute. ([Psy-Fi GPU Texture Painting Design](https://archive.blender.org/wiki/2015/index.php/User:Psy-Fi/GPU_Texture_Painting_Design))

- **Triangulation of the stamp footprint in UV space** is thereby free: the rasterizer clips each face's UV triangle against the framebuffer; the brush footprint = union of per-face UV triangles weighted by screen-space falloff. A stamp crossing a seam is automatically split into per-island fragments (mirroring what the CPU version does per-pixel).
- **Seam bleed on GPU:** offset the UV-space vertex output outward for seam vertices so islands paint N pixels beyond their edge ([same doc](https://archive.blender.org/wiki/2015/index.php/User:Psy-Fi/GPU_Texture_Painting_Design)); plus a post-stroke **dilation pass** for mip/export correctness ([Substance padding doc](https://experienceleague.adobe.com/en/docs/substance-3d-painter/using/technical-support/workflow-issues/export-issues/texture-dilation-or-padding), [uvdilate tool](https://github.com/MattiRegenhardt/uvdilate)).
- **UVs outside 0–1 / UDIM:** UV-space triangles get clipped at tile borders — retesselate triangles whose UVs cross tile boundaries as a preprocess (Blender's answer, [Psy-Fi doc](https://archive.blender.org/wiki/2015/index.php/User:Psy-Fi/GPU_Texture_Painting_Design)); equivalently select tile by `floor(uv)` and split. Mari handles "hundreds of high-resolution texture maps as though they were a single tile" via UDIMs, up to 32K each ([Mari features](https://www.foundry.com/products/mari/features)); implement layers as **texture arrays/atlases indexed per UDIM** with the same dab pipeline, passing tile index per face.
- **Cursor raycast:** brush cursor = ray→mesh pick per input sample (compute-first: a pick pass or persistent BVH on CPU). Occlusion culling ("Occlude With Geometry") prevents painting through the mesh ([Blender options](https://docs.blender.org/manual/en/2.82/sculpt_paint/texture_paint/tool_settings/options.html)); ArmorPaint adds an explicit X-Ray toggle to opt back in ([manual](https://github.com/armory3d/armorpaint_web/blob/main/manual.md)).
- **Mari's alternative — paint buffer:** Mari paints into a screen-space "pane of glass" buffer, then *bakes* it onto the mesh via projection; buffer resolution/depth independent of patch resolution; enables editing paint before commit and 2D transforms ([Paint Buffer](https://learn.foundry.com/mari/Content/user_guide/painting/paint_buffer.html), [how paint applies](https://learn.foundry.com/mari/4.5/Content/user_guide/controlling_paint/controlling_the_way_mari_applies_paint.html)). Adopt as the *projection/stencil tool* architecture, not the freehand brush default (artists expect instant bake-down for freehand strokes).

## 7. Undo architecture

- **Krita:** per-transaction tile mementos in a centralized store; undo stores **copies of entire 64×64 tiles** for touched tiles only; history freed when the QUndoCommand dies; old tiles swapped to disk under pressure ([technical overview](https://github.com/KDE/calligra-history/blob/master/krita/doc/krita_technical_overview.html), [Transactions Design](https://community.kde.org/Krita/Transactions_Design), [KisTileData](https://srcdoc.krita.maou-maou.fr/classKisTileData.html)). Cumulative Undo merges strokes by time rules ([docs](https://docs.krita.org/en/reference_manual/dockers/undo_history.html)).
- **Modern pattern (match our engine):** stroke-as-command with **lazy per-dirty-tile before-capture**: on first write to a tile within a stroke, blit the tile's current content aside (GPU `copyTextureToTexture` tile→staging/texture, no readback to CPU); at stroke end, the command holds {layer, tile ids, before-textures} (+ after for redo). Undo = blit back the tile(s), mark dirty, done. Verified shape from shipped engines: a 256² RGBA8 tile snapshot = 256 KB, "a typical stroke is a fraction of one tile" ([Vixen TerrainStroke](https://vixenengine.org/docs/api/vixen.terrain/terrainstroke)) — at 4K RGBA8 a full layer is 64 MB; a 100-stroke history touching ~6 tiles each ≈ 150 MB worst case, and 64² tiles quarter that. Two design warnings from the same source: capture the **layer**, not the composite (else re-compositing reintroduces the stroke), and **record the rect the kernel read, not just wrote** (smudge/blur sample beyond their footprint).
- **Tile-level before/after** is also how the Saier paint engine upgraded bbox-snapshot undo ("撤销只触达脏 tile" — undo touches only dirty tiles) ([P2-03 tile undo](https://saier-docs.pages.dev/design/tasks/P2-03-tile-undo)).
- **Stroke re-execution** (store dab list + settings, re-run the sim) is the *fallback* for GPU-cheap redo and for the MyPaint-style "modify last stroke" feature; it is deterministic because libmypaint-style states + inputs are replayable (states list is append-only for compatibility, [brushsettings.json](https://github.com/mypaint/libmypaint/blob/master/brushsettings.json)). Keep both: tile snapshots for correctness, replay for storage-light modes.
- GPU readback rule: never read pixels back during interaction. Use async staging buffers at stroke end if CPU copies are needed for save; otherwise undo lives entirely in GPU tile textures with a generation counter.

## 8. Input latency engineering

- **The classic wgpu trap:** acquiring the swapchain texture *before* draining input makes `get_current_texture()` block ~one frame (~16 ms) — reported and analyzed in [wgpu#2269](https://github.com/gfx-rs/wgpu/issues/2269); maintainer-endorsed fix: **acquire the frame at the top of the loop, then process all queued events, then encode with fresh input** (comment by cart), or keep the frame in an `Option` and re-check every iteration. Frame pacing as a first-class problem: [winit#2412](https://github.com/rust-windowing/winit/issues/2412).
- **winit event ordering** (0.30): `NewEvents → (window, device events) → RedrawRequested → AboutToWait` ([winit::event docs](https://docs.rs/winit/0.30.13/aarch64-linux-android/winit/event/index.html)) — so drain pointer events *before* redraw; use `ControlFlow::WaitUntil` to the next vblank estimate rather than busy-poll.
- **Thread separation:** the Windows reference is RealTimeStylus — "provide real-time access to the tablet pen data stream... keep the UI thread from blocking dynamic ink rendering by queuing packet data and making ink collection single threaded" ([MS Learn](https://learn.microsoft.com/en-us/windows/win32/tablet/accessing-and-manipulating-stylus-input)). Concretely: OS events land on the main/winit thread at ~200 Hz; the paint pipeline (filter → sim → dab encode → GPU submit) runs on its own thread fed by a lock-free ring; wgpu `Queue::submit` is `Sync` and can be called from the paint thread. Painting into the layer texture must **not** wait on present — the viewport redraw merely samples the latest layer texture, so input→paint latency is one drain cycle, not one frame.
- Late-latch everything: sample the newest pointer state immediately before encoding the paint compute pass, and again at redraw for the cursor overlay.

## (a) Recommended architecture (Rust + wgpu)

```
┌─ main thread (winit) ───────────────────────────────────────────────────┐
│ event loop: NewEvents → drain pointer ring → RedrawRequested → WaitUntil │
│  · winit 0.30 ordering: https://docs.rs/winit/0.30.13/.../winit/event/  │
│  · frame acquire AFTER event drain (wgpu#2269)                          │
│  · egui/egui_dock UI + 3D viewport: samples layer textures only          │
└────────────┬─────────────────────────────────────────────────────────────┘
             │ lock-free ring (SPSC): {t, x, y, pressure, tilt, buttons}
┌─ paint thread ("strokes scheduler", Krita-shaped) ───────────────────────┐
│ 1. stroke_filter: one-euro x/y + pressure (Casiez) · pull-cursor mode   │
│ 2. brush_sim: libmypaint port — settings+states, inputs→curves→dab       │
│    · spacing: dabs_per_basic/actual_radius + per_second + partial_dabs  │
│ 3. cursor pick: ray→BVH→(tri, barycentric, uv, tile) — cached per sample │
│ 4. projection: stamp disc (screen space) → face set → UV-space          │
│    triangle list (+ seam-bleed offsets, UDIM split by floor(uv))        │
│ 5. dab batch → storage buffer → wgpu compute dispatch per dirty tile    │
│ 6. undo journal: first-write tile blits aside; end-stroke command       │
└────────────┬─────────────────────────────────────────────────────────────┘
             │ wgpu Queue::submit (Sync)
   GPU: layer tile pool (premultiplied RGBA, texture array per UDIM)
        · dab shader: falloff(hardness) × flow × alpha-map, SRC-over
        · wash strokes: per-stroke accumulation texture, ALPHA_DARKEN cap
        · dirty tiles → viewport atlas copy; dilation pass on stroke end
```

**Modules (crates or workspace members):** `brush-input` (winit glue, ring, timestamp normalization) · `brush-filter` (one-euro, pull-cursor, pressure curves) · `brush-core` (libmypaint-semantics sim; settings JSON schema copied from [brushsettings.json](https://github.com/mypaint/libmypaint/blob/master/brushsettings.json)) · `mesh-pick` (raycast, face/disc query, seam adjacency graph) · `brush-project` (screen disc → UV triangles, bleed, UDIM split) · `brush-gpu` (WGSL dab compute, tile pool, wash buffer, dilation) · `paint-doc` (layers, tile store, composite) · `paint-undo` (tile journal, cumulative merge) · `paint-sched` (job queue: CONCURRENT across tiles, BARRIER within a tile).

**Data flow per stylus event:** OS sample (≈200 Hz) → ring → one-euro (≤1 µs) → `stroke_to(x,y,p,dtime)` → 0..N dabs (residual carried) → per dab: pick face set under disc → UV triangles → append to dab batch → per frame: one compute dispatch per dirty tile → viewport redraw (present never blocks paint). Stroke end: wash merge, dilation, undo command commit, cumulative-undo accounting.

**Threading invariants:** UI thread never waits on paint; paint thread never waits on present; within one tile, dab order is sequential (alpha-over is not commutative — dabs are barriered per tile, tiles concurrent, exactly Krita's job typing ([strokes doc](https://docs.krita.org/en/untranslatable_pages/strokes_documentation.html))); wash mode makes dab order irrelevant (temp layer + end merge, Krita's indirect painting ([source](https://krita-artists.org/t/how-to-programmatically-draw-by-pixel-engine/182564/2))) — use it to parallelize freely and to get Substance's "no overlap build-up" behavior.

## (b) Top-5 hardest problems + best known solutions

1. **Seam-continuous stamping.** A screen-space stamp must write both sides of a UV seam consistently, then stay consistent through dilation and mips. Best known: per-face UV-space rasterization of the screen-disc footprint (seam splitting falls out of clipping) ([Psy-Fi design](https://archive.blender.org/wiki/2015/index.php/User:Psy-Fi/GPU_Texture_Painting_Design)) + seam-vertex bleed offsets (same doc) + **3D Space Neighbor padding** for continuous patterns ([Substance Texture Set settings](https://experienceleague.adobe.com/en/docs/substance-3d-painter/using/interface/texture-set/texture-set-settings)); maintain a seam-adjacency map (twin edges → texel pairs) computed at mesh load.
2. **Per-dab sequential compositing at 60 Hz on 8K layers.** Alpha-over is order-dependent; naive per-dab dispatches stall. Best known: wash/temp-layer accumulation for order independence ([Krita](https://docs.krita.org/en/reference_manual/brushes/brush_settings/opacity_and_flow.html)), per-tile barriers with cross-tile concurrency ([Krita strokes](https://docs.krita.org/en/untranslatable_pages/strokes_documentation.html)), dirty-tile-only dispatches with region copies ([partial-update pattern](https://github.com/Makio64/advanced-threejs-tsl-webgpu-rendering)), all-resident-on-GPU ([ArmorPaint](http://armorpaint.org/)).
3. **Making spacing/dynamics feel professional.** Not a slider — a simulation: base+dual-speed low-pass inputs, adaptive spacing via dabs-per-radius, `opaque_linearize` accumulation inversion, residual partial-dab carry ([mypaint-brush.c](https://github.com/mypaint/libmypaint/blob/master/mypaint-brush.c), [brushsettings.json](https://github.com/mypaint/libmypaint/blob/master/brushsettings.json)). Port libmypaint semantics 1:1 (it's the documented gold standard, per-stroke state list included) rather than inventing; add Krita's flow×opacity multiply as the layer on top ([Krita 4.2 change](https://docs.krita.org/en/reference_manual/brushes/brush_settings/opacity_and_flow.html)).
4. **Undo RAM at 4K × 100 steps.** Full-image snapshots = 6+ GB. Best known: dirty-tile before-capture on first write (GPU tile blit, no readback), centralized history freed on command death ([Krita Transactions Design](https://community.kde.org/Krita/Transactions_Design)), swap old historical tiles to disk ([Krita tile system](https://github.com/KDE/calligra-history/blob/master/krita/doc/krita_technical_overview.html)), cumulative merge of stale strokes ([Krita](https://docs.krita.org/en/reference_manual/dockers/undo_history.html)); 64–256 px tiles keep a stroke's cost at "a fraction of one tile" ([Vixen](https://vixenengine.org/docs/api/vixen.terrain/terrainstroke)).
5. **Input-to-photon latency under vsync.** Present-related blocking adds a full frame if done naively ([wgpu#2269](https://github.com/gfx-rs/wgpu/issues/2269)). Best known: drain-then-acquire loop ordering, decouple paint submits from present (paint writes layer texture mid-frame; redraw only samples), real-time stylus stream on its own queue ([MS RealTimeStylus](https://learn.microsoft.com/en-us/windows/win32/tablet/accessing-and-manipulating-stylus-input)), one-euro so smoothing cost is negligible ([CHI'12](https://gery.casiez.net/publications/CHI2012-casiez.pdf)); target <20 ms end-to-end ([threshold](https://us.ktcplay.com/blogs/technology-hub/stylus-latency-threshold-precision-work)).

## (c) Parameter UI — what to copy from MyPaint/Krita/Substance

**From MyPaint ([brushsettings.json](https://github.com/mypaint/libmypaint/blob/master/brushsettings.json), [engine docs](https://www.mypaint.app/en/docs/backend/brush-engine)):**
- The **input→curve editor**: every setting shows base value + expandable per-input curves (pressure, fine/gross speed, tilt, direction, stroke, random, custom). This is the whole editor.
- **Logarithmic radius slider** with px readout (e^x mapping) ([Krita MyPaint docs](https://docs.krita.org/en/reference_manual/brushes/brush_engines/mypaint_engine.html)); `radius_by_random` with its opacity-correction nuance.
- Opacity trio: `opaque` / `opaque_multiply` (pressure entry point) / `opaque_linearize`; hardness + pixel-feather as separate settings; spacing as **dabs per basic radius / actual radius / per second** (never expose a bare "spacing %"); `snap_to_pixel`; smudge group (`smudge`, `smudge_length` + logarithmic multiplier, `smudge_radius`, transparency lock); `slow_tracking` + per-dab variant; inputs incl. `viewzoom` (screen-vs-texture size lock) and `stroke` (duration/hold-time).

**From Krita ([Opacity/Flow](https://docs.krita.org/en/reference_manual/brushes/brush_settings/opacity_and_flow.html), [Options](https://docs.krita.org/en/reference_manual/brushes/brush_settings/options.html), [Sensors], [Freehand tool](https://docs.krita.org/en/reference_manual/tools/freehand_brush.html?highlight=stabilizer)):**
- **Flow and Opacity as separate sliders that multiply** (4.2 semantics) + **Painting Mode: Wash vs Build-up** dropdown — this single pair encodes Substance's flow/stroke-opacity split.
- Tool-level **smoothing picker**: None / Basic / Weighted (distance, stroke-ending, smooth-pressure, scalable-distance) / **Stabilizer (samples@min-speed, samples@max-speed, delay dead-zone, finish-line, stabilize-sensors)** — copy this UI; implement with one-euro + dead zone.
- Sharpness (threshold + soften-edge) for pixel-art; scatter X/Y; airbrush rate; isotropic spacing toggle; sensor types beyond pressure (Fuzzy, Distance, Fade, Perspective) for the curve editor.

**From Substance ([paint brush](https://experienceleague.adobe.com/en/docs/substance-3d-painter/using/painting/paint-tools/paint-brush), [2.5 notes](https://experienceleague.adobe.com/en/docs/substance-3d-painter/using/release-notes/old-versions/version-2-5)):**
- Toolbar shortcuts: Size / Flow / Stroke Opacity / Spacing / Lazy Mouse / Symmetry; per-stamp **jitter quartet** (size, flow, angle, position); **Follow Path** (stamp orientation from previous stamp — document the "needs ≥2 stamps" caveat); **A-key = continue previous stroke** (essential with stroke-opacity); hardness as a remote-controlled alpha-graph parameter.
- Texture-set-level **UV padding mode picker (2D vs 3D Space Neighbor)** and infinite dilation for export ([docs](https://experienceleague.adobe.com/en/docs/substance-3d-painter/using/interface/texture-set/texture-set-settings)).

**Don't copy:** MyPaint's raw setting-count firehose as the default view (hide advanced settings behind expansion); Krita's pre-4.2 additive flow+opacity ([migration note](https://docs.krita.org/en/reference_manual/brushes/brush_settings/opacity_and_flow.html)); Photoshop's opaque 0–100 "smoothing" without a speed-adaptive story ([Adobe](https://helpx.adobe.com/photoshop/desktop/repair-retouch/clean-restore-images/create-smoother-more-polished-brush-strokes-with-stroke-smoothing.html)) — expose one-euro parameters with artistic names instead.
